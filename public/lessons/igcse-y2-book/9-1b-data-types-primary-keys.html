9.1b Data Types & Primary Keys
Six basic data types — and the one field every table needs to uniquely identify each record.
Key Terms
Data type (database)
Classifies how a field's data is stored, displayed, and what operations can be performed on it.
Primary key
A field whose value is NEVER repeated across records — uniquely identifies each one.
Theory

Six basic database data types

  • Text/alphanumeric — a number of characters (letters, digits, symbols).
  • Character — a single character only.
  • Boolean — one of two values: True/False, 1/0, Yes/No.
  • Integer — a whole number, usable in calculations.
  • Real — a decimal number, usable in calculations.
  • Date/time — a date and/or time value.

Choosing types shapes what the database will actually enforce

  • A field's data type determines how it's stored AND what operations make sense on it — an integer field can be used in a calculation; a text field cannot, even if it happens to contain digits.
  • Some validation is automatic once a data type is chosen — e.g. a date/time field automatically rejects an invalid date, before any custom validation rule is even written.
  • Other validation must be set up by the database DEVELOPER — e.g. a WardNumber field needs an explicit rule limiting it to values 1-10; nothing about choosing "integer" alone would enforce that range.

Why every table needs a primary key

  • Every record represents ONE specific item, person, or event — a primary key is the field that reliably, uniquely identifies WHICH one, with no repeats ever allowed.
  • Sometimes an EXISTING field can serve as the primary key, if it's genuinely always unique — e.g. an ISBN in a BOOK table (no two books share the same ISBN).
  • Often, no existing field is guaranteed unique — e.g. in the PATIENT table, two different patients could easily share the same FirstName, FamilyName, even the same DateOfAdmission. In that case, a brand NEW field must be added purely to serve as the primary key.

A worked primary key — HospitalNumber

  • Since no existing PATIENT field is guaranteed unique, a new field, HospitalNumber, is added specifically to serve as the primary key.
  • Its data type is TEXT (not integer) — because a validation rule requires an exact FORMAT: 8 characters, starting with "HN", followed by 6 digits (e.g. HN123456) — a format check like this needs a text field, since a pure integer field couldn't enforce the letter prefix.
Practice — Test Yourself

These questions only cover what THIS subsection taught — the six data types and primary keys.

Short answer 1
Name the six basic database data types.
Reveal answer

Text/alphanumeric, character, Boolean, integer, real, date/time.

Short answer 2
What must ALWAYS be true of a primary key field's values?
Reveal answer

They must never repeat across records — each value must uniquely identify exactly one record.

Fill in the blank 3
A field storing a patient's date of admission would use the ______ data type; a field storing whether a patient has been discharged (yes/no) would use the ______ data type.
Reveal answer

Date/time; Boolean.

Spot the error 4
A student picks FirstName as the primary key for the PATIENT table, reasoning "every patient needs a name anyway". Why is this a bad choice?
Reveal answer

Multiple different patients could easily share the exact same first name (e.g. two patients both called "Sam") — a primary key must be GUARANTEED unique, and a first name alone offers no such guarantee.

Applied / scenario 5
A BOOK table stores Title, Author, and ISBN. Which field should be the primary key, and why?
Reveal answer

ISBN — every real book has a genuinely unique ISBN, unlike Title (different books can share a title) or Author (many books share an author).

Short answer 6
Why is HospitalNumber given a TEXT data type rather than an integer, even though it contains digits?
Reveal answer

Because its required format includes letters (starting with "HN") as well as digits — a pure integer field could never store or validate that format, so a text field is needed.
