8.1c Sequence — Getting the Order Right
The exact same steps, in a different order, produce a completely broken program.
Key Terms
Sequence
The order in which the steps of an algorithm happen — getting it wrong can cause incorrect results or unnecessary extra steps.
Theory

Why sequence is its own genuine skill

  • An incorrect ORDER of otherwise-correct steps can lead to wrong results, or steps that shouldn't even be needed.
  • The algorithm below is meant to input marks (finishing when 999 is entered), then output the total, average, and how many real marks were entered.
⚠ Version 1 — looks reasonable, but the SEQUENCE is wrongDECLARE Total, Average : REAL DECLARE Mark, Counter : INTEGER Total ← 0 Mark ← 0 Counter ← 0 OUTPUT "Enter marks, 999 to finish " REPEAT INPUT Mark Total ← Total + Mark IF Mark = 999 THEN Average ← Total / Counter ENDIF Counter ← Counter + 1 UNTIL Mark = 999 OUTPUT "The total mark is ", Total OUTPUT "The average mark is ", Average OUTPUT "The number of marks is ", Counter

OUTPUT: The total mark is 1074 / The average mark is 358 / The number of marks is 4

Every single output is wrong — here's exactly why

  • Test data: 25, 27, 23, 999 (three real marks, then the "finish" signal).
  • The 999 itself gets ADDED into Total (75 + 999 = 1074) — the algorithm never checks to exclude it, because Total ← Total + Mark runs BEFORE the check for whether Mark equals 999.
  • Counter reaches 4 (counting the 999 as if it were a real mark), not 3 — so the "number of marks" output is wrong too.
  • Average is calculated using the WRONG Total (1074, which includes 999) divided by the WRONG Counter (4) — every downstream value inherits the earlier mistake.
✓ Version 2 — same task, correct sequenceDECLARE Total, Average : REAL DECLARE Mark, Counter : INTEGER Total ← 0 Mark ← 0 Counter ← -1 OUTPUT "Enter marks, 999 to finish " REPEAT Total ← Total + Mark INPUT Mark Counter ← Counter + 1 UNTIL Mark = 999 OUTPUT "The total mark is ", Total Average ← Total / Counter OUTPUT "The average mark is ", Average OUTPUT "The number of marks is ", Counter

What actually changed, and why each change fixes the bug

  • Counter starts at -1 instead of 0 — this allows for the extra "999" input that triggers the end of the loop WITHOUT it being counted as a real mark. By the time the loop ends, Counter has correctly counted only the 3 real marks.
  • Total ← Total + Mark now runs BEFORE the new INPUT Mark — so on each pass, the OLD mark (from the PREVIOUS input) gets added to Total, one step behind. This means when 999 is finally input, it triggers the loop to end on the NEXT check, but it is never itself added to Total (the addition for that pass already happened using the previous real mark).
  • The IF check inside the loop is removed entirely — Average is now calculated ONCE, after the loop ends, using the final correct Total and Counter — there's no need to test "is this the last input?" inside the loop at all.
  • All three outputs are now correct: total = 75 (25+27+23), average = 25, number of marks = 3.
Practice — Test Yourself

These questions only cover what THIS subsection taught — how sequence errors happen and how this specific one was fixed.

Short answer 1
In Version 1, why does 999 end up being added into Total?
Reveal answer

Because Total ← Total + Mark runs immediately after every INPUT, before there's any check for whether Mark equals 999 — by the time the algorithm checks for 999, it has already been added to the total.

Short answer 2
Why does Counter start at -1 in the corrected version, instead of 0?
Reveal answer

So that the extra "999" input (which does still get counted once, to trigger the loop's exit) doesn't throw off the final count of REAL marks — starting one lower cancels out that one extra increment.

Fill in the blank pseudocode 3
In the corrected version, which line comes FIRST inside the loop: Total ← Total + Mark or INPUT Mark?
Reveal answer

Total ← Total + Mark comes first — it adds the PREVIOUS mark to the total before a new one is input, which is exactly what keeps 999 from ever being added.

Spot the error 4
A student "fixes" Version 1 by just removing the IF check but leaving everything else (including Counter starting at 0, and the original line order) unchanged. Would this genuinely fix the algorithm? Why or why not?
Reveal answer

No — removing only the IF check doesn't fix the core sequence problem: Total ← Total + Mark would still run immediately after every input, so 999 would still get added to Total, and Counter would still count it as a 4th mark. The REAL fix requires changing the ORDER of the lines (Total updates using the previous mark, before the new input), not just deleting one check.

Applied / scenario 5
Using the corrected Version 2 algorithm, trace through the test data 10, 20, 30, 40, 999. What would the three final outputs be?
Reveal answer

Total mark = 100 (10+20+30+40), average mark = 25 (100 ÷ 4), number of marks = 4.

Short answer 6
What's the general lesson this worked example teaches about writing algorithms?
Reveal answer

The exact same set of steps, in a different ORDER, can produce a completely different (and wrong) result — sequence is a genuine, separate skill from just knowing which individual steps are needed; getting the order right is just as important as choosing the right operations.
