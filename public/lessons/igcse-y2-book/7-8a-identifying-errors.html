7.8a Identifying Errors in Algorithms
Using a trace table to catch a bug — then fixing the algorithm so it genuinely works for ANY data.
Key Terms
Logic error
An algorithm that runs without crashing, but produces the WRONG result for some (or all) inputs.
Provisional value
A starting value assigned to a variable before the real data is known, used as a placeholder until real values are compared against it.
Theory

Trace tables reveal bugs, not just confirm correctness

  • Trace tables and test data can be used to identify AND correct errors — not just to prove an algorithm works.
  • The algorithm below is meant to find the highest and lowest of ten numbers (the same shape as Section 7.7's algorithm), tested with: 400, 800, 190, 170, 300, 110, 600, 150, 130, 900.

Reading the completed trace: the bug is real and specific

  • The output is 900, 100 — but the SMALLEST number in the list is actually 110, which never got picked up. There is an error: the smallest number, 110, has not been identified.
  • Notice C (the running minimum) never changes from its starting value of 100 anywhere in the trace — every single input value (400, 800, 190, 170, 300, 110, 600, 150, 130, 900) is LARGER than 100, so the condition X < C is never true, not even once.
  • This is a genuine logic error, not a crash — the algorithm runs to completion and produces AN answer, just the wrong one.

Why this happens: the algorithm only works for 0-100

  • The original algorithm initialises B ← 0 and C ← 100 — provisional values that only make sense for percentage marks in the range 0 to 100.
  • Tested with numbers like 400 and 900, which are already bigger than the provisional C = 100, the minimum-tracking logic breaks immediately.
Attempt 2 — bigger provisional bounds (still not a real fix)A ← 0 B ← -1000000 C ← 1000000 REPEAT INPUT X IF X > B THEN B ← X ENDIF IF X < C THEN C ← X ENDIF A ← A + 1 UNTIL A = 10 OUTPUT B, C

A much larger range — but still not a genuine fix

  • This version works for a much larger range of numbers than the original — but it STILL does not work for every possible set of numbers. Any number bigger than 1,000,000 or smaller than -1,000,000 would break it exactly the same way.
  • Choosing "big enough" provisional bounds is really just guessing — there is always some data that breaks a fixed bound, no matter how large.
Attempt 3 — a genuine fix: start from the first real valueCounter ← 1 INPUT Number Highest ← Number Lowest ← Number REPEAT INPUT Number IF Number > Highest THEN Highest ← Number ENDIF IF Number < Lowest THEN Lowest ← Number ENDIF Counter ← Counter + 1 UNTIL Counter = 9 OUTPUT Highest, Lowest

Why THIS version genuinely works for any set of numbers

  • Highest and Lowest are set to the value of the FIRST item input — not a guessed provisional bound — so they always start from a value that's actually PART of the real data.
  • The remaining values are then compared against this real starting point, one at a time.
  • The counter now needs to reach only 9 (not 10) — because the first value was already used to set the initial Highest/Lowest, so only the remaining 9 values need to be looped over and compared.
  • This is a standard, reusable technique: whenever the range of valid data isn't known in advance, initialise using the FIRST real value rather than a guessed bound.
Practice — Test Yourself

These questions only cover what THIS subsection taught — using trace tables to find bugs, and fixing an algorithm to work for genuinely any data.

Short answer 1
In the completed trace table, what specific error was identified?
Reveal answer

The smallest number in the list, 110, was never identified — C (the running minimum) stayed at its starting value of 100 the whole way through, since every real input value was larger than 100.

Short answer 2
Why did increasing the provisional bounds to -1,000,000 / 1,000,000 not count as a genuine fix?
Reveal answer

It only works for a LARGER range of numbers, not every possible set of numbers — any input still bigger or smaller than those bounds would break it in exactly the same way. Guessed bounds can always be exceeded by some data.

Fill in the blank pseudocode 3
Complete the genuine fix's initialisation: INPUT Number
Highest ← ______
Lowest ← ______
Reveal answer

Highest ← Number and Lowest ← Number — both set to the first real value input, not a guessed bound.

Spot the error 4
In Attempt 3, why does the loop now run UNTIL Counter = 9 instead of 10, even though there are still 10 numbers in total?
Reveal answer

Because the FIRST number was already consumed before the loop began (to set the initial Highest/Lowest) — only the remaining 9 numbers are read and compared inside the loop, so the counter only needs to reach 9.

Applied / scenario 5
Using Attempt 3's algorithm and the test data -97, 12390, 0, 77, 359, -2, -89, 5000, 21, 67 — what would the final OUTPUT be?
Reveal answer

12390, -97 — Highest ends at 12390 (the largest value in the list), Lowest ends at -97 (the smallest — note it's also the FIRST value input, so it was never actually beaten by a smaller one, but the algorithm still correctly identifies it since it started from a real value).

Short answer 6
What general lesson does this trace-table exercise teach about testing an algorithm?
Reveal answer

An algorithm that runs without crashing and produces SOME output is not automatically correct — it must be tested against real, varied data (not just data that happens to suit its assumptions) using a trace table, to reveal logic errors that would otherwise go unnoticed.
