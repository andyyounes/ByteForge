7.1a The Program Development Life Cycle
Analysis, design, coding, and testing — the four stages every program passes through before it's finished.
Key Terms
Requirements specification
A clear statement of exactly what a program needs to do, produced during analysis.
Abstraction
Keeping only the key elements needed for the solution, discarding unnecessary detail.
Decomposition
Breaking a complex problem into smaller, easier-to-solve parts.
Iterative testing
Testing a module, fixing it, and re-testing repeatedly until it works as required.
Theory

The four stages covered in this chapter and the next

  • The full program development life cycle has FIVE stages: analysis, design, coding, testing, and maintenance.
  • This chapter (and Chapter 8) focus on the first FOUR: analysis, design, coding, testing.

Analysis

  • Before solving any problem, it must be clearly DEFINED so everyone working on it understands what's needed — this is the requirements specification.
  • Analysis uses two key tools: abstraction and decomposition.
  • Abstraction: keep only the key elements needed for the solution, discard unnecessary detail. Example: a map only shows what's needed for travelling from A to B — a road map and a rail map show completely different details for the same journey, because each is abstracted for a different purpose.
  • Decomposition: break a complex problem into smaller parts, which can be subdivided further until each part is easy to solve. Example: "getting dressed" decomposes into: select items to wear → remove clothes being worn → put selected items on in order.

Design

  • Uses the requirements specification from analysis to show HOW the program should be developed.
  • By the end of design, the programmer should know: what needs to be done, how each task is performed, and how the tasks work together.
  • Formally documented using structure charts, flowcharts, and pseudocode.

Coding and iterative testing

  • The program (or set of programs) is developed — each MODULE is written in a suitable language, then tested to check it works.
  • Iterative testing: modular tests are run, code is amended, and tests repeated until the module performs as required — a genuine repeat cycle, not a one-shot check.

Testing

  • The COMPLETED program (or set of programs) is run many times with DIFFERENT sets of test data.
  • This ensures all the tasks work together correctly, exactly as specified in the design.
Worked example — abstraction in maps

A road map for driving between two towns shows roads, junctions, and distances — details a DRIVER needs. A rail map for the same journey shows stations and lines — details a TRAIN PASSENGER needs. Both are abstractions of the same real geography, each keeping only what's relevant to its purpose and discarding the rest.

Practice — Test Yourself

These questions only cover what THIS subsection taught — the program development life cycle (analysis, design, coding, testing).

Short answer 1
What are the four stages of the program development life cycle covered in this chapter and the next?
Reveal answer

Analysis, design, coding, and testing.

Short answer 2
Explain the difference between abstraction and decomposition.
Reveal answer

Abstraction keeps only the key elements needed for a solution, discarding unnecessary detail (e.g. a map showing only what's relevant to travel). Decomposition breaks a complex problem into smaller, more manageable parts.

Fill in the blank pseudocode 3
______ testing means modular tests are conducted, code is amended, and tests are ______ until the module performs as required.
Reveal answer

Blank 1: Iterative. Blank 2: repeated.

Spot the error 4
A student claims: "Testing only needs to happen once, right at the very end, using a single set of test data." What does this get wrong?
Reveal answer

Two things: testing happens iteratively DURING coding (module by module, repeated until each works), and the final testing stage explicitly uses MULTIPLE different sets of test data run MANY times — not a single one-off check.

Applied / scenario 5
A team is asked to build a program that manages a school's timetable. Using this lesson's content, describe what should happen in the ANALYSIS stage before any code is written.
Reveal answer

The team should produce a clear requirements specification stating exactly what the program needs to do, using abstraction (keeping only the details genuinely relevant to timetabling, discarding irrelevant information) and decomposition (breaking "manage the timetable" into smaller sub-problems, e.g. assigning teachers, assigning rooms, avoiding clashes) — all BEFORE any coding begins.

Short answer 6
What must a programmer know by the end of the design stage?
Reveal answer

What needs to be done (all the tasks), how each task is to be performed, and how the tasks work together.
