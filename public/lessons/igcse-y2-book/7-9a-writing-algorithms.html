7.9a Writing and Amending Algorithms
A real process for going from a problem statement to a working, tested algorithm.
Key Terms
Sub-problem
A smaller, more manageable piece a complex problem is broken down into.
Structure diagram
A diagram showing how a problem is broken into sub-tasks, top-down.
Theory

The eight stages of producing an algorithm

  1. Make sure the problem is CLEARLY SPECIFIED — the purpose of the algorithm and the tasks it must complete.
  2. Break the problem down into sub-problems — most problems, even simple ones, can be divided into: set-up processes, input, processing of data, permanent storage of data (if required), output of results.
  3. Decide how data is obtained and stored, what happens to it, and how results are displayed.
  4. Design the structure of the algorithm using a structure diagram.
  5. Decide how to construct the algorithm — flowchart or pseudocode (or follow whatever you're told to use).
  6. Construct the algorithm so it can be easily read and understood by someone else — set it out clearly, use MEANINGFUL names for data stores, and take particular care with loop/selection conditions (e.g. Counter >= 10 rather than "Counter ten or over").
  7. Use several sets of test data (Normal, Abnormal, and Boundary) to dry run the algorithm and record results in trace tables, to find any errors.
  8. If errors are found, correct them and repeat the process until the algorithm works perfectly.

Structure diagrams vs. flowcharts — different jobs

  • A structure diagram (or "structure chart") shows WHAT sub-tasks make up a solution, top-down — it says nothing about loops, conditions, or exact sequencing.
  • A flowchart or pseudocode then shows HOW each of those sub-tasks is actually built, step by step, including every loop and decision.
  • Precision matters when writing an algorithm exactly as much as when writing real program code — meaningful names and clearly stated conditions make an algorithm something another person (or you, months later) can actually follow.
Worked example — concert ticket pricing

Tickets are sold for a concert at $20 each. Buying 10 tickets gives a 10% discount; buying 20 tickets gives a 20% discount. No more than 25 tickets can be bought in a single transaction.

a) Pseudocode for the ticket-pricing algorithmREPEAT OUTPUT "How many tickets would you like to buy? " INPUT NumberOfTickets UNTIL NumberOfTickets > 0 AND NumberOfTickets < 26 IF NumberOfTickets < 10 THEN Discount ← 0 ELSE IF NumberOfTickets < 20 THEN Discount ← 0.1 ELSE Discount ← 0.2 ENDIF ENDIF Cost ← NumberOfTickets * 20 * (1 – Discount) PRINT "Your tickets cost ", Cost

b) How this algorithm would be tested

  • Test data would use values of: 0, 26 — expected result: both REJECTED (outside the valid 1-25 range).
  • 1, 25 — expected results: 20, 400 (1 ticket at full price = $20; 25 tickets at 20% off = 25 × 20 × 0.8 = $400).
  • 9, 10 — expected results: 180, 180 (9 tickets at full price = $180; 10 tickets at 10% off = 10 × 20 × 0.9 = $180 — genuinely the same cost, right at the discount boundary).
  • 19, 20 — expected results: 342, 320 (19 tickets at 10% off = 19 × 20 × 0.9 = $342; 20 tickets at 20% off = 20 × 20 × 0.8 = $320).
  • Notice this test data is exactly boundary data — pairs straddling each discount threshold (0/1, 9/10, 19/20, 25/26).
Practice — Test Yourself

These questions only cover what THIS subsection taught — the algorithm-writing process and the ticket-pricing worked example.

Short answer 1
What is the very FIRST stage in producing an algorithm, before any design work begins?
Reveal answer

Making sure the problem is clearly specified — understanding the purpose of the algorithm and exactly what tasks it must complete.

Short answer 2
What is the difference in job between a structure diagram and a flowchart/pseudocode?
Reveal answer

A structure diagram shows WHAT sub-tasks a solution breaks into (top-down), with no detail on loops or conditions. A flowchart or pseudocode shows HOW each sub-task is actually built, step by step, including every loop and decision.

Fill in the blank pseudocode 3
Complete the ticket cost formula: Cost ← NumberOfTickets * 20 * (1 – ______)
Reveal answer

Cost ← NumberOfTickets * 20 * (1 – Discount).

Spot the error 4
A student names their loop condition variable Counter and writes the exit condition as "keep going until Counter reaches ten or so". Why does stage 6 of the process explicitly warn against this?
Reveal answer

"Ten or so" is vague and not a precise, checkable condition — a real algorithm needs an EXACT comparison like Counter >= 10, otherwise it's ambiguous exactly when the loop should stop, and different people (or a computer) could interpret it differently.

Applied / scenario 5
Using the ticket-pricing algorithm, what would the output be for 10 tickets, and why is this a genuinely useful boundary test?
Reveal answer

10 tickets triggers the 10% discount (since it's NOT less than 10): 10 × 20 × 0.9 = $180. It's a useful boundary test because 9 tickets (just below) costs 9 × 20 = $180 too — proving the discount threshold behaves exactly as intended right at the edge, not one ticket too early or late.

Short answer 6
Why does the test data for this algorithm specifically include the pairs 0/1, 9/10, 19/20, and 25/26?
Reveal answer

Because each pair straddles a real boundary in the algorithm's logic (the minimum valid order, and each discount threshold) — boundary data always comes in pairs like this, one value accepted and one rejected (or one at each discount rate), to prove the exact cut-off point behaves correctly.
