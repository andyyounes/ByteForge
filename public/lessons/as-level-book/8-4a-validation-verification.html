8.04 Data Validation and Verification
Validation checks the SHAPE of data, not its truth — then three transmission-checking methods, ending with one that can actually locate and fix an error. Completes Chapter 8.
Key Terms
Validation
A check that data entered is of the correct type and format; does NOT guarantee accuracy.
Verification
Confirmation of data received by a system.
Theory

"Validation" is a misleading name — it doesn't mean "correct"

  • If a name is expected but the WRONG name is entered, it's still recognised AS a name — so it passes validation despite being factually wrong.
  • Validation can only catch data that is the wrong TYPE, wrong FORMAT, or OUT OF RANGE — never data that's simply untrue but plausible.

Five types of validation check

  • Presence check — an entry field isn't left blank.
  • Format check — e.g. a date must be dd/mm/yyyy.
  • Length check — e.g. a telephone number has the right number of digits.
  • Range check — e.g. a month value must not exceed 12.
  • Type check — e.g. only a numeric value accepted for a month.

Verification — confirming, not correcting

  • Most common example: re-entering a new password to confirm it.
  • Verification is USUALLY effective — but does NOT guarantee accuracy either, because the SAME wrong data could be entered both times.

Verification during data transfer — checking for flipped bits

  • Data corruption during transmission typically happens at bit level — an individual bit flips from 1 to 0 or vice versa.
  • Verification techniques check some property of the bit pattern to catch this.

Method 1 — simple one-bit parity check (using even parity)

  1. At the transmitter: count the 1s in the 7-bit code.
  2. If the count is even, set the parity bit to 0.
  3. If the count is odd, set the parity bit to 1.
  4. Repeat for every byte.
  5. At the receiver: count the 1s in the full 8-bit code.
  6. If the count is even, accept the byte.
  7. Repeat for every byte.
  • Limitation: it can only DETECT the presence of an error — it cannot identify WHICH bit is wrong. Also, if exactly TWO bits flip in one byte, the error goes undetected (though this is unlikely enough to be a reasonable risk to accept). If an error is found, re-transmission must be requested.

Method 2 — the checksum method

  • A block of bytes is defined at the transmitter. The bits across the whole block are interpreted as one binary number, summed, and the SUM is sent as a checksum value.
  • The receiver does the same calculation and compares it against the transmitted checksum.
  • Same limitation as simple parity: an error can be DETECTED, but its exact POSITION cannot be determined.

Method 3 — the parity block check (can locate AND correct an error)

  • A longitudinal parity check on a serial sequence of bits across several bytes, arranged as a MATRIX.
  • Each byte (row) gets its OWN parity bit, exactly as in Method 1.
  • An EXTRA byte (the parity byte) is then created — each of ITS bits is the parity for that BIT POSITION down the whole column (including the row-parity column itself).
  • If exactly ONE bit is wrong anywhere in the block, the ROW check and the COLUMN check will each flag exactly one line — and their INTERSECTION identifies precisely which bit is wrong, so it can be corrected without needing a re-transmission.
Worked Example — locating a flipped bit with a parity block check

Three 4-bit data bytes are sent using even parity, row-by-row AND column-by-column:

bit4bit3bit2bit1row parity
Byte A10111
Byte B01100
Byte C11000
Parity byte00011
  • Check: Byte A = 1011 (three 1s, odd) → row parity 1 ✓. Byte B = 0110 (two 1s, even) → row parity 0 ✓. Byte C = 1100 (two 1s, even) → row parity 0 ✓.
  • Column bit1 across A,B,C = 1,0,0 (one 1, odd) → column parity 1 ✓ — every row and column checks out before transmission.
Now suppose bit2 of Byte B is flipped in transit (1 → 0)

Byte B is received as 0100 instead of 0110.

bit4bit3bit2bit1row parity
Byte A10111 ✓
Byte B (received)01000 ✗
Byte C11000 ✓
Parity byte0 ✓0 ✓0 ✗1 ✓1
  • Row check: Byte B's data now has one 1 (odd), but its transmitted parity bit says 0 (expects even) — ROW B is flagged.
  • Column check: bit2 down the column is now 1, 0, 0 (one 1, odd), but the parity byte says 0 (expects even) — COLUMN bit2 is flagged.
  • The INTERSECTION of the flagged row and flagged column is exactly Byte B's bit2 — that is the bit that was flipped. It can be corrected back to 1 without needing to ask for a re-transmission.
Practice — Test Yourself

These questions only cover what THIS subsection taught — validation, verification, and the three transmission-checking methods (completes Section 8.04 and Chapter 8).

Short answer 1
Why can validation never guarantee that entered data is actually TRUE?
Reveal answer

Validation only checks type, format, and range — a wrong-but-plausible value (like the wrong name, still recognised as a valid-looking name) will still pass every validation check.

Short answer 2
What is the shared limitation of BOTH the simple one-bit parity check and the checksum method?
Reveal answer

Both can only DETECT that an error occurred somewhere — neither can identify the exact position of the error.

Fill in the blank 3
In a parity block check, the intersection of the flagged ______ and the flagged ______ identifies the exact bit that is wrong.
Reveal answer

Row; column.

Spot the error 4
A student says: "Verification guarantees data accuracy, since the user has to enter the data twice and it's checked both times." What's wrong?
Reveal answer

Verification only confirms the SAME value was entered twice — it cannot catch a case where the user makes the SAME mistake both times. It does not guarantee accuracy, only consistency between the two entries.

Applied / scenario 5
In the worked example, if the ROW check flags Byte B but the COLUMN check flags NO column at all, what would that suggest happened instead of a single flipped data bit?
Reveal answer

It would suggest the error is in Byte B's OWN parity bit itself (not in its data), since the row parity fails but no data column's overall parity is disturbed.

Short answer 6
Which validation check would catch someone entering "13" for a month field, and which would catch entering "May" instead of a number?
Reveal answer

A range check would catch "13" (out of the valid 1-12 range); a type check would catch "May" (not numeric, when a number is expected).
