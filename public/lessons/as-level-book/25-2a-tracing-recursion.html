25.03 Tracing a Recursive Subroutine
Following calls down to the base case, then back up as they "unwind".
Theory

Tracing a simple case — CountDownFrom

PROCEDURE CountDownFrom(n : INTEGER) OUTPUT n IF n > 0 THEN CALL CountDownFrom(n - 1) ENDIF END PROCEDURE
Call #CallOUTPUTn>0
1CountDownFrom(3)3TRUE
2CountDownFrom(2)2TRUE
3CountDownFrom(1)1TRUE
4CountDownFrom(0)0FALSE
  • Here, everything happens BEFORE the recursive call, so a simple downward trace is enough.

The tricky case: statements AFTER the recursive call

PROCEDURE CountUpTo(n : INTEGER) IF n > 0 THEN CALL CountUpTo(n - 1) ENDIF OUTPUT n END PROCEDURE
  • CRITICAL insight: statements AFTER the recursive call are NOT executed until control RETURNS to that point — i.e., as the recursive calls "UNWIND" back up.
  • Tracing CountUpTo(3): calls go DOWN (3→2→1→0, no output yet at each), reach the base case at n=0 (output 0), then UNWIND back up — call 1 (n=1) resumes and outputs 1, call 2 (n=2) resumes and outputs 2, call 3 (n=3) resumes and outputs 3.
  • Result: outputs appear in the order 0, 1, 2, 3 — the REVERSE of the calling order, precisely because the OUTPUT happens on the way back UP.

Tracing convention — never go back and edit earlier rows

  • When showing the "unwind" in a trace table, ADD NEW rows for each unwinding call (often labelled with the call number in brackets, e.g. "(3)", "(2)", "(1)") — do NOT go back and retroactively fill in earlier rows.
  • This keeps it clear exactly WHEN each output actually occurred in the real execution sequence.

Tracing a recursive FUNCTION — the RETURN statement

  • A recursive FUNCTION has a statement after the recursive call too: the RETURN statement.
  • Tracing Factorial(4): calls go DOWN to Factorial(0) (base case, Result=1). Then UNWINDING: Factorial(1) computes 1×1=1 and returns 1; Factorial(2) computes 2×1=2 and returns 2; Factorial(3) computes 3×2=6 and returns 6; Factorial(4) computes 4×6=24 and returns 24.
  • A useful alternative visualisation: nest each call inside a BOX. The innermost box computes first; its result FEEDS UP into the next box outward, and so on until the outermost box completes.
Practice — Test Yourself

These questions only cover what THIS subsection taught — tracing recursive procedures and functions (completes Section 25.03).

Short answer 1
Why does CountUpTo(3) output values in the order 0, 1, 2, 3, rather than 3, 2, 1, 0?
Reveal answer

Because the OUTPUT statement comes AFTER the recursive call — it only executes as each call resumes while UNWINDING back up, starting from the base case (0) and working back out to the original call (3).

Short answer 2
What statement in a recursive FUNCTION plays the same "executes after the recursive call" role that OUTPUT plays in CountUpTo?
Reveal answer

The RETURN statement.

Fill in the blank 3
When tracing the unwinding of recursive calls, you should ______ new rows rather than editing earlier ones.
Reveal answer

Add.

Spot the error 4
A student traces CountUpTo(2) and writes down the output as "2, 1, 0" because that's the order the calls were MADE in. What's wrong?
Reveal answer

The OUTPUT statement runs AFTER the recursive call, so outputs happen in the order calls UNWIND (finish), not the order they were made. The correct output order is "0, 1, 2".

Applied / scenario 5
In tracing Factorial(4), what value does the innermost call, Factorial(0), return, and what happens to it next?
Reveal answer

It returns 1 (the base case). This value is then used by Factorial(1) to compute 1 × 1 = 1, which it returns to Factorial(2), and so on, propagating upward through each unwinding call.

Short answer 6
In the "nested boxes" visualisation of recursive calls, which box's result is computed first?
Reveal answer

The innermost box (representing the base case) — its result then feeds outward into each enclosing box in turn.
