10.05 A Logical Entity-Relationship Model
A foreign key can't hold many values — so a many-to-many relationship needs a link entity.
Theory

From conceptual to logical — why the conversion is needed

  • A fully-annotated ER diagram is a CONCEPTUAL model — it doesn't relate to any specific implementation.
  • To implement as a relational database, it must be converted to a LOGICAL model. Start from a simplified ER diagram showing just cardinalities.

How each cardinality converts

  • 1:M — needs NO further refinement. The entity at the MANY end simply gets a foreign key referencing the primary key of the entity at the ONE end.
  • 1:1 — has implementation options, but is extremely rare in practice (not discussed further).
  • M:M — the genuinely PROBLEM case. A foreign key can only hold a SINGLE value, so it cannot represent "many" references at once.

The solution — a link entity

  • For an M:M relationship (like Band↔Booking), create a LINK ENTITY in between — here, "Band-Booking".
  • The link entity holds TWO foreign keys: one referencing Band's primary key, one referencing Booking's primary key.

Choosing primary keys once every entity is a table

  • Every entity in the logical ER diagram becomes a table — primary and foreign keys can now be chosen for each, summarised in a KEY TABLE.
  • The link entity CANNOT use just BandName or just BookingID alone as primary key (neither is unique enough on its own) — but the COMBINATION of the two works as a compound primary key.

Practice — Test Yourself

These questions only cover what THIS subsection taught — converting a conceptual ER model into a logical one (completes Section 10.05).

Short answer 1
Why can't a plain foreign key be used to implement a many-to-many relationship?
Reveal answer

A foreign key attribute can only hold a SINGLE value — it cannot represent the "many" references that an M:M relationship requires on either side.

Short answer 2
How many foreign keys does a link entity resolving an M:M relationship typically have, and what do they reference?
Reveal answer

Two — one referencing the primary key of each of the two original entities in the M:M relationship.

Fill in the blank 3
A 1:M relationship needs no link entity — the entity at the ______ end simply receives a foreign key referencing the entity at the ______ end.
Reveal answer

Many; one.

Spot the error 4
A student proposes using just BandName alone as the Band-Booking link table's primary key. Why won't this work?
Reveal answer

A single band can appear in MULTIPLE bookings, so BandName alone repeats across many rows in the link table — it isn't unique on its own. Only the COMBINATION of BandName and BookingID together is guaranteed unique.

Applied / scenario 5
Why does a logical ER diagram not necessarily produce a set of tables already in 3NF (as mentioned at the end of this section)?
Reveal answer

A logical ER diagram only guarantees a set of entities consistent with the relationships and their cardinalities (roughly 2NF-level structure) — it doesn't automatically check for non-key dependencies between attributes, which is what normalisation to 3NF specifically addresses.

Short answer 6
What is a "key table" used for?
Reveal answer

Summarising the chosen primary key and foreign key(s) for every table in the database design, once every entity has become a table.
