16.02 File Organisation
Serial, sequential, and direct-access files — how records are stored and found again.
Theory

Text files vs. binary files

  • A TEXT file stores data using a defined character code (Chapter 1) — it can be created and read with any text editor.
  • A BINARY file stores data in its INTERNAL representation (e.g. an integer stored as two's complement in two bytes) — it requires a specific program to create and interpret it.
  • A binary file's organisation is built from RECORDS, and each record is built from FIELDS, each holding one value.
Binary file: a file designed for storing data to be used by a computer program.
Record: a collection of fields containing data values.

Serial files

  • Records have NO defined order — a new record is simply appended as it arrives (e.g. a bank's raw transaction log, in chronological order but not otherwise sorted).
  • A text file is a KIND of serial file, but differs: it has repeating LINES defined by end-of-line characters, with no separate end-of-record character.

Sequential files

  • Records ARE ordered — suited to long-term storage, and comparable to a database as an alternative storage method.
  • Requires a KEY FIELD whose values are unique and SEQUENTIAL, but not necessarily consecutive. This differs from a database's primary key, which must be unique but NOT sequential.
  • A specific record is found by reading key-field values in order until the target is reached — inherently slower for large files than direct access.

Direct-access (hashed) files

  • Sometimes called "random-access" — but the randomness is just that access ISN'T defined by reading sequentially, not that positions are literally random.
  • A HASHING ALGORITHM converts a key-field value into a calculated POSITION in the file — allowing (near-)immediate access for large files.
  • Hashing can produce COLLISIONS (two different keys hashing to the same position) — when this happens, the next available position is used instead, meaning a search may need an initial direct access followed by a LIMITED serial search.
  • A simple hashing method for a numeric key: divide by a suitably large number and use the REMAINDER as the position.

File access — reading, editing, deleting

  • Serial file: read record by record, successively, until the target is found.
  • Sequential file: similar, but only the key-field value needs reading at each step.
  • Direct-access file: the key value is submitted to the SAME hashing algorithm used at input time, giving the same position back.
  • Editing/deleting a SEQUENTIAL file: a NEW version of the whole file is normally created, copying records across until the target is reached, then continuing with the edit/deletion applied.
  • Editing/deleting a DIRECT-ACCESS file: no new file is needed (unless it becomes full) — a deleted record is simply FLAGGED so future reads skip over it.
Practice — Test Yourself

These questions only cover what THIS subsection taught — text/binary files, and serial/sequential/direct-access organisation (completes Section 16.02).

Short answer 1
What is the key difference between a sequential file's key field and a database table's primary key?
Reveal answer

A sequential file's key field values must be unique AND sequential (in order). A database primary key must be unique, but does NOT need to be sequential.

Short answer 2
What is a hashing algorithm used for in a direct-access file?
Reveal answer

Converting a key-field value into a calculated position in the file, allowing a record to be located quickly without a full sequential search.

Fill in the blank 3
A ______ file has records with no defined order; a ______ file has records ordered by a unique, sequential key field.
Reveal answer

Serial; sequential.

Spot the error 4
A student says direct-access files are called "random-access" because records are placed at genuinely RANDOM positions in the file. What's the misconception?
Reveal answer

The "random" in random-access doesn't mean the position is arbitrary — it means access is NOT restricted to reading sequentially. The actual position is calculated DETERMINISTICALLY by a hashing algorithm from the key field, so the same key always produces the same position.

Applied / scenario 5
A bank needs to record every withdrawal and deposit as it happens throughout the day, with no need to search for a specific past transaction quickly. Which file organisation fits best, and why?
Reveal answer

Serial — transactions just need appending in the order they occur; there's no requirement for fast individual lookups, which is exactly what serial organisation is well suited to (e.g. batch processing or backup).

Short answer 6
Why might two different keys hash to the same calculated position, and what happens when that occurs?
Reveal answer

Because a hashing algorithm can't guarantee unique positions for every possible key — this is called a collision. When it happens, the next available position in the file is used instead, meaning a later search may need a direct access followed by a short serial search.
