23.02 Binary Search
Searching an ordered list by repeatedly halving the search area — like looking up a word in a dictionary.
Theory

The dictionary analogy

  • Looking up "quicksort" in a dictionary, you don't start at the beginning — you check the MIDDLE, see whether your word comes before or after it, and discard the HALF that can't contain it.
  • Repeat on the remaining half, checking ITS middle, until the word is found — or there's nothing left to check.
Binary search: repeated checking of the middle item in an ordered search list and discarding the half of the list which does not contain the search item.

Binary search in pseudocode

Found ← FALSE SearchFailed ← FALSE First ← 1 Last ← MaxItems WHILE NOT Found AND NOT SearchFailed Middle ← (First + Last) DIV 2 IF List[Middle] = SearchItem THEN Found ← TRUE ELSE IF First >= Last // no search area left THEN SearchFailed ← TRUE ELSE IF List[Middle] > SearchItem THEN Last ← Middle - 1 // must be in first half ELSE First ← Middle + 1 // must be in second half ENDIF ENDIF ENDIF ENDWHILE IF Found = TRUE THEN OUTPUT Middle ELSE OUTPUT "Item not present in array" ENDIF
  • Each iteration either FINDS the item, or moves ONE of the two boundaries (First or Last) to eliminate half the remaining search area.
  • The search FAILS when First >= Last with no match found — there's no search area left to check.

Why binary search needs an ORDERED list

  • The decision "which half to discard" only makes sense because the list is SORTED — comparing against the middle value tells you definitively which half the target must be in, ONLY if order is guaranteed.
  • An UNORDERED list has no such guarantee — only a LINEAR search (checking every item) works there.

Why binary search is so much faster

  • Each comparison roughly HALVES the remaining search space — so the number of comparisons needed grows only LOGARITHMICALLY with list size, not linearly.
  • A linear search of n items takes, on average, about n/2 comparisons. A binary search takes roughly log₂(n) — for a million items, that's around 20 comparisons instead of half a million.
Practice — Test Yourself

These questions only cover what THIS subsection taught — binary search (part of Section 23.02).

Short answer 1
What condition must a list satisfy before binary search can be used on it?
Reveal answer

The list must be ORDERED (sorted) — binary search relies on knowing which half of the list a value must fall in, based on a comparison with the middle item.

Short answer 2
In the pseudocode, what condition indicates the search has failed?
Reveal answer

First >= Last, with the item still not found — meaning there's no search area left to check.

Fill in the blank 3
A linear search of n items takes on average about ______ comparisons; a binary search takes roughly ______.
Reveal answer

n/2; log₂(n).

Spot the error 4
A student tries to binary-search an UNSORTED array and gets an incorrect result. What went wrong?
Reveal answer

Binary search's core assumption — that comparing against the middle value tells you which half the target is in — completely breaks down if the list isn't sorted. The algorithm may discard the half that actually contains the target.

Applied / scenario 5
Dry-run binary search for the value 60 in the ordered list [7,12,19,23,27,33,37,41,45,56,59,60,62,71,75,80,84,88,92,99] (20 items, First=1, Last=20). What is Middle on the first iteration, and which half does the search move to?
Reveal answer

Middle = (1+20) DIV 2 = 10, so List[10] = 56. Since 56 < 60, First moves to Middle+1 = 11 — the search continues in the second half.

Short answer 6
Why can binary search be considered more efficient than linear search for large, ordered lists?
Reveal answer

Each comparison eliminates HALF of the remaining items, so the number of comparisons needed grows only logarithmically with the list size — far fewer comparisons are needed than checking items one by one, especially as the list grows large.
