30.04 Test Plans and Test Data
Normal, abnormal, and boundary data — and why one test should only ever check ONE thing.
Theory

Why a test PLAN, not just ad-hoc testing

  • Large programs CANNOT be exhaustively tested — a systematic PLAN is needed to find as many errors as possible with limited testing effort.
  • An OUTLINE plan considers: does flow of control give the right choices and route to the right module? Is INPUT validated correctly? Do loops/decisions behave correctly? Is data saved to the correct files? Are RESULTS correct?
  • This outline then becomes a DETAILED test plan, specifying exact test DATA.

Three types of test data

TypeMeaning
Normal (valid)Typical data values that ARE valid and should be accepted
Abnormal (erroneous)Data values the system should NOT accept
Boundary (extreme)Values right at the edge of the valid range — both just WITHIN (valid) and just OUTSIDE (invalid) the boundary

Worked example — testing the pyramid program's "number of symbols" input

  • Requirement: the number must be a POSITIVE ODD integer, greater than 1.
  • NORMAL: e.g. 7 — an odd positive integer, should be accepted. Test SEVERAL different valid values, not just one.
  • ABNORMAL: needs SEVERAL separate tests, each checking ONE specific reason for rejection: −7 (negative integer), 8 (even integer), 7.5 (real number), '*' (non-numeric).
  • CRITICAL principle: NEVER combine two abnormal conditions into one test (e.g. one negative EVEN number) — if it's rejected, you won't know WHICH reason actually caused the rejection.
  • BOUNDARY: the smallest possible pyramid is 1 symbol — so 1 is just WITHIN the boundary. This also raises genuine DESIGN questions: should 0 be accepted? Is there an UPPER boundary too (e.g. based on screen width — 79 within, 81 outside, if 80 characters fit per line)?
  • Testing WITHIN the boundary also happens to test NORMAL data, just at the extreme end of the valid range.
Practice — Test Yourself

These questions only cover what THIS subsection taught — test plans and the three types of test data (completes Section 30.04).

Short answer 1
Why can't large programs be tested exhaustively?
Reveal answer

The number of possible input combinations and code paths is far too large to check every single one — a systematic test plan aims to find as many errors as possible within realistic effort, not to guarantee every case is covered.

Short answer 2
What are boundary (extreme) test values?
Reveal answer

Values at the very edge of the range of normal data — including one value just WITHIN the boundary (should be accepted) and one just OUTSIDE it (should be rejected).

Fill in the blank 3
A test that combines two different abnormal conditions in one input (e.g. a negative EVEN number) risks not revealing WHICH ______ actually caused the rejection.
Reveal answer

Reason (condition).

Spot the error 4
A tester picks −8 as their ONE abnormal test value for the pyramid program's number-of-symbols input, intending to test that both negative numbers AND even numbers are rejected. What's the flaw?
Reveal answer

−8 is BOTH negative AND even — if it's correctly rejected, there's no way to know whether the program checks for negative numbers, even numbers, both, or neither correctly. Separate tests (e.g. −7 for negative, 8 for even) are needed to isolate each condition.

Applied / scenario 5
If a screen fits 80 characters per line, what are the two boundary test values for the maximum number of pyramid symbols, and which is valid?
Reveal answer

79 (just within the boundary — valid) and 81 (just outside the boundary — should be rejected).

Short answer 6
Why should more than one normal (valid) test value be used, rather than just one?
Reveal answer

A single valid value might accidentally pass even if the program has a subtle bug that only shows up with a DIFFERENT valid value — testing multiple normal values increases confidence the logic is genuinely correct, not just correct by coincidence for one case.
