10.06 Normalisation
"The key, the whole key, and nothing but the key" — one booking data sheet, taken all the way to 3NF.
Key Terms
Repeating group
A set of attributes with more than one set of values when the other attributes each have a single value.
Theory

The starting point — a real booking data sheet

  • Attribute list: (BookingID, VenueName, VenueAddress1, VenueAddress2, Date, (BandName, NumberOfMembers, Headlining))
  • The INNER brackets around BandName/NumberOfMembers/Headlining mark a REPEATING GROUP — one booking can have several bands, each with their own member count and headlining status.
  • A table needs single rows and atomic values, so a repeating group CAN'T sensibly go straight into one table — the only naive option is a row per band-within-a-booking, which duplicates the booking/venue/date data for every band.

Step 1 — First Normal Form (1NF): eliminate the repeating group

  • Split into two tables — one for the non-repeating attributes, one for the repeating group.
Booking(BookingID, VenueName, VenueAddress1, VenueAddress2, Date) Band-Booking(BandName, BookingID(fk), NumberOfMembers, Headlining)
  • The repeating-group table needs a COMPOUND primary key AND a foreign key back to the first table.
  • Result: no data redundancy in EITHER table, and every attribute is dependent on ITS table's primary key — that's the essence of 1NF.

Step 2 — Second Normal Form (2NF): remove partial dependencies

  • Only tables with a COMPOUND primary key need checking — Booking is automatically already in 2NF.
  • For each non-key attribute, ask: is it dependent on BOTH parts of the compound key, or just one?
  • NumberOfMembers is dependent ONLY on BandName (not on BookingID too) — so it must move to a NEW table.
Booking(BookingID, VenueName, VenueAddress1, VenueAddress2, Date) Band-Booking(BandName(fk), BookingID(fk), Headlining) Band(BandName, NumberOfMembers)
  • A table is in 2NF if it either has a single-attribute primary key, or a compound key where every non-key attribute depends on BOTH parts.

Step 3 — Third Normal Form (3NF): remove non-key dependencies

  • Check every table for a NON-KEY attribute that depends on ANOTHER non-key attribute (not on the primary key itself).
  • VenueAddress1 and VenueAddress2 are dependent on VenueName — not directly needed by BookingID itself — so they move to a new Venue table.
Band(BandName, NumberOfMembers) Band-Booking(BandName(fk), BookingID(fk), Headlining) Booking(BookingID, Date, VenueName(fk)) Venue(VenueName, VenueAddress1, VenueAddress2)
  • These four 3NF table definitions match four of the entities already identified in the logical ER model — though this alignment WON'T always happen automatically.
The one-sentence summary of 3NF

Each non-key attribute is dependent on the key, the WHOLE key, and NOTHING BUT the key.

Practice — Test Yourself

These questions only cover what THIS subsection taught — normalisation to 1NF, 2NF, and 3NF (completes Section 10.06).

Short answer 1
What problem does converting to 1NF specifically solve?
Reveal answer

It eliminates the repeating group — splitting the data so no table needs multiple values for one attribute within a single row.

Short answer 2
In the 2NF step, why did NumberOfMembers move out of Band-Booking into its own Band table?
Reveal answer

NumberOfMembers is dependent ONLY on BandName, not on the whole compound key (BandName + BookingID) — a partial dependency, which 2NF requires moving into a separate table.

Fill in the blank 3
In a 3NF table, every non-key attribute is dependent on the key, the ______ key, and ______ but the key.
Reveal answer

Whole; nothing.

Spot the error 4
A student says: "VenueAddress1 and VenueAddress2 should stay in the Booking table, since a booking has to happen somewhere." Why does 3NF move them out instead?
Reveal answer

The addresses are dependent on VenueName — a NON-KEY attribute of Booking — not on BookingID itself. That's exactly the non-key dependency 3NF removes: the addresses belong with Venue, referenced from Booking via a foreign key.

Applied / scenario 5
Why does the un-normalised single table (BookingID, Venue data, Date, BandName, NumberOfMembers, Headlining all together) cause data redundancy?
Reveal answer

Because one booking can have MULTIPLE bands, the BookingID, venue data, and date all get repeated once PER band in that booking — exactly the redundancy visible in the two-row example (Cambridge International Theatre's address repeated for both ComputerKidz and ITWizz).

Short answer 6
Does a logical ER diagram always automatically produce a 3NF set of tables?
Reveal answer

No — a logical ER diagram will describe a 2NF set of entities, but not necessarily a 3NF set. Normalisation must still be checked/applied separately.
