15.03 Testing Strategies
Stub testing, black-box testing, and white-box testing — three ways to hunt for logic and run-time errors.
Theory

Logic errors and run-time errors

  • Syntax errors are easy — the compiler/interpreter finds them and hints at the fix.
  • Much harder: a LOGIC ERROR (causes the program not to behave as intended) and a RUN-TIME ERROR (causes the program to crash or freeze). Both are only found through careful testing.
  • The danger: these errors may only appear under CERTAIN circumstances — a program that seems to work fine, then fails on rare data, is far harder to catch than one that crashes every time.
Logic error: an error in the logic of the solution that causes it not to behave as intended.
Run-time error: an error that causes program execution to crash or freeze.

Stub testing

  • Used to test a user interface BEFORE all facilities are fully implemented.
  • Each "stub" procedure body contains just an OUTPUT statement acknowledging the call was made — the real logic is filled in later.
  • Lets you confirm the overall menu/control structure works correctly before investing time coding every feature.

Black-box testing

  • Testing done by someone who does NOT see the program code and doesn't know how it was coded — the program is a "black box".
  • The tester looks at the SPECIFICATION to determine what the program should do, then devises test data (normal, boundary, and erroneous values) and works out the EXPECTED results.
  • If actual results don't match expected results, a problem exists — but black-box testing alone doesn't reveal WHICH lines of code are at fault; white-box methods (Sections 15.04–15.05) are needed for that.
Test data: carefully chosen values that will test a program.
Black-box testing: comparing expected results with actual results when a program is run.

White-box testing

  • Testing EVERY PATH through the program code — this requires knowledge of the code's internal structure, unlike black-box testing.
White-box testing: testing every path through the program code.

Worked example — choosing white-box test data for a nested IF

INPUT Number1 INPUT Number2 INPUT Number3 IF Number1 > Number2 THEN IF Number1 > Number3 THEN OUTPUT Number1 ELSE OUTPUT Number3 ENDIF ELSE IF Number2 > Number3 THEN OUTPUT Number2 ELSE OUTPUT Number3 ENDIF ENDIF
  • To exercise every path, four sets of test data are needed: (1) first number largest, (2) first number bigger than second, third is largest, (3) second number largest, (4) second number bigger than first, third is largest.
  • It doesn't matter what EXACT values are chosen — only that the relative sizes force each branch of the nested IF to run at least once.
Practice — Test Yourself

These questions only cover what THIS subsection taught — logic/run-time errors, stub testing, black-box, and white-box testing (completes Section 15.03).

Short answer 1
What is the key difference between black-box and white-box testing?
Reveal answer

Black-box testing is done without seeing the code, comparing expected vs. actual results against the specification. White-box testing requires seeing the code, and aims to exercise every possible path through it.

Short answer 2
What does the body of a "stub" procedure typically contain?
Reveal answer

Just an output statement that acknowledges the procedure was called — the real logic isn't implemented yet.

Fill in the blank 3
Test data usually consists of three categories: ______ values, ______ values, and ______ values.
Reveal answer

Normal; boundary; erroneous.

Spot the error 4
A tester runs a nested-IF program with only ONE set of test data where the first number happens to be the largest, and declares the program fully tested. What's wrong with this approach?
Reveal answer

Only one path through the nested IF has been exercised — several other branches (e.g. where the second or third number is largest) remain completely untested, so bugs in those paths would go undetected. Proper white-box testing requires data that exercises EVERY path.

Applied / scenario 5
Why is it dangerous that a logic error might only appear under rare circumstances?
Reveal answer

If a program appears to work correctly most of the time, the error could go unnoticed for a long time — potentially causing serious consequences before it's finally triggered by unusual data or a rarely-used feature.

Short answer 6
What do black-box testers use to determine what a program is meant to do?
Reveal answer

The program specification.
