26.03 Random-Access File Processing
Storing records directly at a hashed address, so they can be updated in place. Completes Section 26.03.
Theory

Why use random access?

  • Instead of storing records in an ARRAY and periodically saving the whole thing, each record can be written STRAIGHT to a binary file as it's created.
  • This allows UPDATING a record IN SITU — read it, change it, save it back to the SAME location — without rewriting the whole file.
  • IMPORTANT restriction: this only works for FIXED-LENGTH records (so every record occupies a predictable, identical amount of space).

Using a hashing function to calculate the address

  • Exactly like a hash table (Chapter 23): a HASHING FUNCTION calculates an address from the record's KEY, and the record is stored there.
  • COLLISIONS can occur just as with a hash table — a colliding record is stored in the NEXT FREE record space.

Worked example — saving and retrieving a random-access record

// Saving a record OPENFILE "CarFile" FOR RANDOM Address ← Hash(ThisCar.VehicleID) SEEK "CarFile", Address PUTRECORD "CarFile", ThisCar CLOSEFILE "CarFile" // Retrieving a record OPENFILE "CarFile" FOR RANDOM Address ← Hash(ThisCar.VehicleID) SEEK "CarFile", Address GETRECORD "CarFile", ThisCar CLOSEFILE "CarFile"
  • SEEK moves a pointer to the given record ADDRESS. PUTRECORD/GETRECORD then act at THAT address. After the command runs, the pointer automatically advances to the NEXT record in the file.

A practical detail — addressing by BYTE position

  • In Python and VB.NET, the hashing function must account for the record's SIZE IN BYTES. If a record is 58 bytes, the SECOND record slot starts at byte position 59; the n-th slot starts at (n-1) × 58 + 1.
  • In Pascal, this is handled automatically: the file is declared to hold a SPECIFIC record type, and addresses are simply SLOT numbers (Pascal computes the actual byte offset internally).
Practice — Test Yourself

These questions only cover what THIS subsection taught — random-access file processing (completes Section 26.03).

Short answer 1
Why does random-access record storage only work for fixed-length records?
Reveal answer

The address calculation relies on every record occupying a predictable, identical amount of space — variable-length records would make it impossible to reliably calculate where the n-th record's byte position actually starts.

Short answer 2
What does the SEEK command do?
Reveal answer

Moves a pointer to a given record address within the file, so the next PUTRECORD/GETRECORD acts at that specific location.

Fill in the blank 3
For a record size of 58 bytes, the n-th record slot starts at byte position ______.
Reveal answer

(n - 1) × 58 + 1.

Spot the error 4
A student writes records of VARYING lengths (some names are longer than others) to a random-access file, then wonders why records become corrupted when read back. What's the root cause?
Reveal answer

Random-access file storage assumes FIXED-LENGTH records so addresses can be reliably calculated — varying record lengths break the assumption that record n starts at a predictable byte offset, causing reads to land in the wrong place or overlap with neighbouring records.

Applied / scenario 5
Why can Pascal's programmer simply use a "slot number" as the address, while Python/VB.NET programmers must calculate an exact byte offset?
Reveal answer

Pascal's file declaration (file of CarRecord) tells the language the exact record type and size in advance, so it can automatically translate a slot number into the correct byte offset internally — Python and VB.NET don't have this built-in typed-file mechanism, so the programmer must do the byte-position arithmetic manually.

Short answer 6
What happens to a hash collision in a random-access file, similar to a hash table?
Reveal answer

The colliding record is stored in the next free record space, just like open hashing in a hash table.
