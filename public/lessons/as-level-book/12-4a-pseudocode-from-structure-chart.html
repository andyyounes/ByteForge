12.04 Deriving Pseudocode from a Structure Chart
The same pyramid problem, rebuilt properly this time with parameters instead of global variables. Completes Chapter 12.
Theory

Why go back and redo the pyramid example

  • Worked Example 12.02 (Section 12.02) used procedures, but ALL its variables were GLOBAL.
  • This time, LOCAL variables and PARAMETERS are used instead — making every module genuinely self-contained.
  • Parameters are supplied in PARENTHESES after the module's identifier when it's called.
MODULE Pyramid CALL SetValues(NumberOfSymbols, NumberOfSpaces, Symbol, MaxNumberOfSymbols) REPEAT CALL OutputSpaces(NumberOfSpaces) CALL OutputSymbols(NumberOfSymbols, Symbol) CALL AdjustValuesForNextRow(NumberOfSpaces, NumberOfSymbols) UNTIL NumberOfSymbols > MaxNumberOfSymbols ENDMODULE PROCEDURE SetValues(NumberOfSymbols, NumberOfSpaces, Symbol, MaxNumberOfSymbols) INPUT Symbol CALL InputMaxNumberOfSymbols NumberOfSpaces ← (MaxNumberOfSymbols - 1) / 2 NumberOfSymbols ← 1 END PROCEDURE PROCEDURE InputMaxNumberOfSymbols(MaxNumberOfSymbols) REPEAT INPUT MaxNumberOfSymbols UNTIL MaxNumberOfSymbols MOD 2 = 1 END PROCEDURE PROCEDURE OutputSpaces(NumberOfSpaces) FOR Count ← 1 TO NumberOfSpaces OUTPUT Space // without moving to next line ENDFOR END PROCEDURE PROCEDURE OutputSymbols(NumberOfSymbols, Symbol) FOR Count ← 1 TO NumberOfSymbols OUTPUT Symbol // without moving to next line ENDFOR OUTPUT Newline // move to the next line END PROCEDURE PROCEDURE AdjustValuesForNextRow(NumberOfSpaces, NumberOfSymbols) NumberOfSpaces ← NumberOfSpaces - 1 NumberOfSymbols ← NumberOfSymbols + 2 END PROCEDURE

What changed, and why it's better engineering

  • Every module's variables are now declared as PARAMETERS in its own definition line — nothing relies on a variable simply existing "somewhere" globally.
  • This directly mirrors the structure chart's downward/upward arrows from Section 12.03 — each arrow IS a parameter appearing in the pseudocode.
  • Benefit: a module can be tested, reused, or modified WITHOUT worrying that it might silently affect an unrelated global variable elsewhere in the program.
Practice — Test Yourself

These questions only cover what THIS subsection taught — deriving pseudocode with parameters from a structure chart (completes Section 12.04 and Chapter 12).

Short answer 1
Where are a module's parameters written when it is CALLED?
Reveal answer

In parentheses, immediately after the module's identifier.

Short answer 2
What was the main weakness of the Section 12.02 version of the pyramid solution, that this section fixes?
Reveal answer

All its variables were GLOBAL — this version instead uses local variables and parameters, making every module self-contained.

Fill in the blank 3
Using local variables and parameters means a module is ______ — changes inside it can't accidentally affect a variable elsewhere in the solution.
Reveal answer

Self-contained.

Spot the error 4
A student writes PROCEDURE OutputSpaces with NO parameters at all, but still expects it to know the current NumberOfSpaces value. Why won't this work in this parameter-based design?
Reveal answer

Without NumberOfSpaces declared as a parameter, the procedure has no LOCAL way to receive that value — in a design built around parameters rather than globals, the value must be explicitly passed in, e.g. PROCEDURE OutputSpaces(NumberOfSpaces).

Applied / scenario 5
How does a structure chart's downward arrow relate directly to this pseudocode's syntax?
Reveal answer

A downward arrow representing a parameter passed INTO a module corresponds exactly to that parameter appearing in the module's own parameter list, e.g. NumberOfSpaces appearing in PROCEDURE OutputSpaces(NumberOfSpaces).

Short answer 6
Which module in the pyramid solution has NO parameters that feed data back UP to a calling module?
Reveal answer

OutputSpaces and OutputSymbols — both simply perform output actions using the parameters passed IN, without needing to return any new value back up.
