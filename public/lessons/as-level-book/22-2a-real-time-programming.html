22.02 Real-Time Programming
Two worked pseudocode examples: a monitoring loop, and a full monitoring-and-control loop.
Theory

The core requirement: repetitive, timed sensor reading

  • A monitoring/control program needs an INFINITE (or very long-running) loop that reads sensors REPEATEDLY, for as long as the system is switched on.
  • Reading sensors every single clock cycle is unnecessarily frequent — the program must control the TIMING, either via a timed sequence or a deliberate DELAY inside the loop.

Worked example — a pure monitoring program

EndReadingSensor ← FALSE ReadingOutOfRange ← FALSE REPEAT CALL SensorRead(SensorValue) IF SensorValue > MaximumAllowed THEN ReadingOutOfRange ← TRUE Reading ← 'H' ELSE IF SensorValue < MinimumAllowed THEN ReadingOutOfRange ← TRUE Reading ← 'L' ENDIF ENDIF IF ReadingOutOfRange THEN CALL WarningDisplay(Reading) ENDIF ReadingOutOfRange ← FALSE // reset — crucial! FOR TimeFiller ← 1 TO 999999 // deliberate delay loop ENDFOR UNTIL EndReadingSensor
  • Key features: an effectively INFINITE loop; a "do-nothing" inner loop purely to create a DELAY; a warning procedure called only when needed; and — critically — ReadingOutOfRange is RESET to FALSE after each check, otherwise the warning would fire repeatedly forever once triggered once.

Worked example — a monitoring AND control program

EndReadingSensor ← FALSE READ DesiredOutputLevel REPEAT CALL SensorRead(SensorValue) SensorDifference ← DesiredOutputLevel - SensorValue IF ABS(SensorDifference) < DesiredOutputLevel/100 THEN SensorDifference ← 0 // treat tiny differences as "close enough" ENDIF IF SensorDifference > 0 THEN ActuatorAdjustmentFactor ← SensorDifference/DesiredOutputLevel AdjustmentDirection ← 'up' CALL ActivateActuator(AdjustmentDirection, ActuatorAdjustmentFactor) ENDIF IF SensorDifference < 0 THEN ActuatorAdjustmentFactor ← ABS(SensorDifference)/DesiredOutputLevel AdjustmentDirection ← 'down' CALL ActivateActuator(AdjustmentDirection, ActuatorAdjustmentFactor) ENDIF FOR TimeFiller ← 1 TO 999999 ENDFOR UNTIL EndReadingSensor
  • The actuator is only activated when the sensor reading shows a SIGNIFICANT change (beyond the small tolerance band) — avoiding constant, unnecessary micro-adjustments.
  • CRITICAL assumption: the code only works correctly if the actuator's effect on the property is GUARANTEED to happen before the NEXT loop iteration reads the sensor again — otherwise the feedback loop would be acting on stale or incomplete information.
Practice — Test Yourself

These questions only cover what THIS subsection taught — real-time monitoring/control loops (completes Section 22.02).

Short answer 1
Why is a "do-nothing" FOR loop included at the end of the monitoring loop?
Reveal answer

To create a deliberate delay before the sensor is read again — reading it every single clock cycle would be unnecessarily (and wastefully) frequent.

Short answer 2
Why must ReadingOutOfRange be reset to FALSE after the warning is displayed?
Reveal answer

Because the loop continues running indefinitely — without resetting it, the warning procedure would be called repeatedly on every subsequent iteration, even after the original problem might have been resolved.

Fill in the blank 3
In the monitoring-and-control example, if the sensor difference is within ______% of the desired output level, it is treated as effectively zero.
Reveal answer

1 (one) — the tolerance check is DesiredOutputLevel/100.

Spot the error 4
A student removes the ABS(SensorDifference) < DesiredOutputLevel/100 tolerance check, arguing the actuator should react to ANY difference no matter how tiny. What problem could this cause?
Reveal answer

The actuator would be triggered constantly by insignificant fluctuations (sensor noise, tiny natural variation) — causing unnecessary wear, instability, or "hunting" behaviour, instead of settling once close enough to the target.

Applied / scenario 5
Why is it essential that the actuator's effect completes BEFORE the next sensor reading, in the monitoring-and-control loop?
Reveal answer

If the next reading happens before the actuator's adjustment has actually taken effect, the controller would be reacting to OUTDATED information — potentially over-correcting or issuing contradictory adjustments based on a measurement that doesn't yet reflect the previous action.

Short answer 6
What determines whether the AdjustmentDirection is set to 'up' or 'down'?
Reveal answer

The sign of SensorDifference — positive (actual reading below desired) sets 'up'; negative (actual reading above desired) sets 'down'.
