30.03 Testing Methods
From a single module's dry-run all the way to a customer's final sign-off.
Theory

A quick recap from Chapter 15

  • Logic errors and run-time errors; BLACK-BOX and WHITE-BOX testing; IDE debugging facilities; dry-running with a trace table — this last technique is ALSO called a "WALKTHROUGH".
  • These methods are used EARLY in development — e.g. testing individual MODULES as they're written, often by the PROGRAMMERS themselves. In larger organisations, dedicated SOFTWARE TESTERS are employed instead.

Integration testing — do the pieces work TOGETHER?

  • Individual modules might each pass ALL their own tests — but when JOINED together into one program, the WHOLE must still be tested, since modules can interact in unexpected ways.
  • Usually done INCREMENTALLY: add one module at a time, test again, THEN add the next.
Integration testing: individually tested modules are joined into one program and tested to ensure the modules interact correctly.

Alpha, acceptance, and beta testing — different customers, different processes

StageWho testsContext
Alpha testingIn-house, dedicated testersBefore release to ANY external party
Acceptance testingThe specific customerBespoke software — customer checks it meets THEIR requirements before signing off
Beta testingA limited group of chosen external usersGeneral-sale software with no single customer — feedback drives fixes before full release
  • Bespoke software (built for ONE specific customer) goes through ACCEPTANCE testing as part of the HAND-OVER process — successful acceptance testing means the customer SIGNS OFF the software.
  • General-sale software has no single customer to sign off — so after alpha testing, a BETA version is released to chosen BETA TESTERS, who feed back problems from their own real-world environments.
Alpha testing: testing of software in-house by dedicated testers.
Acceptance testing: testing of software by customers before sign-off.
Beta testing: testing of software by a limited number of chosen users before general release.
Practice — Test Yourself

These questions only cover what THIS subsection taught — integration, alpha, acceptance, and beta testing (completes Section 30.03).

Short answer 1
Why is integration testing necessary even when every individual module has already passed its own tests?
Reveal answer

Modules can interact in unexpected ways once combined — passing in isolation doesn't guarantee they work correctly TOGETHER as a whole program.

Short answer 2
What is the key difference between acceptance testing and beta testing?
Reveal answer

Acceptance testing is done by ONE specific customer for BESPOKE software, ending in formal sign-off. Beta testing is done by a LIMITED group of chosen external users for GENERAL-SALE software, with no formal sign-off — just feedback.

Fill in the blank 3
Integration testing is usually carried out ______, adding one module at a time and re-testing before adding the next.
Reveal answer

Incrementally.

Spot the error 4
A software house building a general-sale mobile app plans to skip beta testing and go straight from alpha testing to full public release, since "there's no specific customer to sign it off anyway". What's the flaw in this reasoning?
Reveal answer

The absence of a single customer is exactly WHY beta testing exists — it substitutes for acceptance testing by getting real-world feedback from a limited group of actual users across DIVERSE environments before the full release, catching problems in-house testers might miss.

Applied / scenario 5
A company builds custom payroll software for one specific client. Which testing stage involves that client directly, and what happens at the end of it if successful?
Reveal answer

Acceptance testing — the client checks it meets their requirements, and on success, they sign off the software as part of the hand-over process.

Short answer 6
What is another name used for dry-running a program by working through it and recording steps in a trace table?
Reveal answer

A walkthrough.
