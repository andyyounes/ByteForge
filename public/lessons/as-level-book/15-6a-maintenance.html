15.06–15.07 Corrective & Adaptive Maintenance
Fixing bugs vs. extending functionality — the two reasons a finished program still gets changed. Completes Chapter 15 and the AS portion of the course.
Theory

Corrective maintenance

  • Maintaining software is NOT like maintaining a mechanical device — code doesn't wear out or need "lubricating".
  • CORRECTIVE maintenance is the work required when a program isn't working correctly, due to a logic error or a run-time error.
  • Errors sometimes stay hidden for a long time, because the affected part of the program is rarely used, or because the triggering data only shows up under extreme/unusual circumstances.
  • To FIND a bug, a programmer uses either IDE debugging features (Section 15.04) or a trace table (Section 15.05).
Corrective maintenance: correcting identified errors.

Adaptive maintenance

  • ADAPTIVE maintenance means amending a program to make it perform functions it was NOT originally designed to do.
  • Example from Chapter 12: a two-player Connect 4 game could be adapted so ONE player is the computer — a genuine change in functionality, not a bug fix.
  • This kind of change is made either to ENHANCE functionality, or in response to a change in the original SPECIFICATION.
Adaptive maintenance: amending a program to enhance functionality or in response to specification changes.

Telling the two apart

  • Ask: "Is the program doing something WRONG (a bug), or is it doing exactly what it was designed to do, but we now want it to do MORE (a new requirement)?"
  • The first case is corrective maintenance; the second is adaptive maintenance. The distinction matters because the APPROACH differs — corrective maintenance starts from tracing an existing error, while adaptive maintenance starts from designing new algorithm/data-structure changes from scratch.

Chapter 15 summary

  • The program development cycle: problem-solving, design, coding, translation, execution, testing.
  • IDE features: prettyprint, context-sensitive prompts, dynamic syntax checks, collapsible code blocks.
  • Testing strategies: stub testing, black-box testing (specification-driven, no code visibility), white-box testing (every code path exercised).
  • Locating errors: IDE debugging tools (breakpoints, single-stepping, watch windows) or dry-running with a trace table.
  • Maintenance: corrective (fixing bugs) vs. adaptive (extending functionality or meeting new specification requirements).
Practice — Test Yourself

These questions cover corrective and adaptive maintenance, and draw together the whole of Chapter 15 (completes Sections 15.06–15.07 and Chapter 15).

Short answer 1
What is the key difference between corrective and adaptive maintenance?
Reveal answer

Corrective maintenance fixes an existing error so the program works as originally intended. Adaptive maintenance changes the program to do something it was NOT originally designed to do — enhancing functionality or responding to a new specification.

Short answer 2
Name the two techniques mentioned for finding the cause of a reported bug.
Reveal answer

Using IDE debugging features (breakpoints, single-stepping, watch windows), or dry-running the algorithm with a trace table.

Fill in the blank 3
Unlike a mechanical device, software doesn't ______ out or need lubricating — but it can still develop bugs that require ______ maintenance.
Reveal answer

Wear; corrective.

Spot the error 4
A team labels "adding a single-player mode against the computer to Connect 4" as corrective maintenance. Why is this the wrong label?
Reveal answer

The original two-player program isn't broken — nothing needs "correcting". Adding entirely new functionality (a computer opponent) that wasn't part of the original design is a textbook example of ADAPTIVE maintenance, not corrective.

Applied / scenario 5
A payroll program has worked fine for years, but a bug appears only when an employee's salary is exactly £0 (a rare edge case). Why is this a classic example of why hidden bugs are dangerous?
Reveal answer

Because the triggering data (a £0 salary) is so rare, the bug could remain undiscovered for years — and by the time it surfaces, it may already have caused real, hard-to-trace consequences, unlike a bug that crashes the program every single time it runs.

Short answer 6
Which testing approach (black-box or white-box) would most directly help you locate the exact LINE of code responsible for an already-confirmed bug?
Reveal answer

White-box testing — it requires and uses knowledge of the code's internal structure to trace exactly which path (and therefore which line) is at fault, unlike black-box testing which only confirms THAT a bug exists.
