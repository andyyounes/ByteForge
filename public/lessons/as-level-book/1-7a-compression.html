1.07 Compression Techniques & Multimedia Packaging
Huffman coding, run-length encoding, and why video needs an entirely different approach — completes Chapter 1.
Key Terms
Lossless compression
Reduces file size with NO information lost — decoding recreates the exact original file.
Lossy compression
Reduces file size by discarding some information permanently — the exact original can never be recovered.
Prefix property
No Huffman code is the starting sequence of any other code — guarantees unambiguous decoding.
Multimedia container format
A single file format holding several independent but synchronised streams (video, audio, subtitles, etc.).
Theory

Lossless vs. lossy — the fundamental choice

  • Text files MUST use lossless compression — losing even one character's information would corrupt the meaning, so it's never acceptable.
  • Sound and image files can often tolerate LOSSY compression, since the human ear/eye may not notice some detail being removed or altered.
  • Many real applications combine BOTH lossless and lossy methods together.

Huffman coding — shorter codes for more frequent characters

  • Instead of giving every character a fixed one-byte code, Huffman coding analyses which characters occur MOST often, and gives THOSE shorter codes — genuinely variable-length codes, not one fixed size.
  • The original byte stream becomes a genuine BIT stream (codes no longer align to byte boundaries).

The prefix property — why decoding is never ambiguous

  • Critically, NONE of the codes begins with the exact bit sequence of any OTHER (shorter) code — this is the "prefix property".
  • Because of this, a decoder reading the bit stream left to right can ALWAYS tell exactly where one code ends and the next begins, with zero ambiguity — even though codes have different lengths.

Run-length encoding (RLE) — a different lossless approach

  • RLE converts a SEQUENCE of the same repeated bit pattern into a code recording just the pattern AND how many times it repeats.
  • This is particularly effective for bitmap files, which often contain large runs of identical or near-identical pixel colours (e.g. a plain background).

A simple example of lossy compression

  • Reducing the COLOUR DEPTH of a bitmap (fewer bits per pixel) is a straightforward lossy technique — detail is genuinely discarded, but the human eye may barely notice on typical images.
Spatial redundancyRedundant information WITHIN a single frame/image (e.g. large areas of the same colour). Image-compression techniques (like RLE) target this.
Temporal redundancyRedundant information BETWEEN successive video frames — one frame is often very similar to the one before it.

Why video needs a genuinely different compression strategy

  • Only tackling spatial redundancy (treating each frame as an independent image) is INEFFICIENT for video — it ignores the fact that consecutive frames are usually very similar to each other.
  • A much more effective approach targets TEMPORAL redundancy instead: rather than storing every frame in full, mainly record the DIFFERENCES between adjacent frames.

Multimedia container formats — packaging audio and video together

  • A video contains BOTH images and sound — but these two streams don't go to the same part of a receiving/display system, so they must be handled independently, while still staying SYNCHRONISED.
  • The solution is a multimedia CONTAINER format — one file holding multiple independent streams (video, audio, and potentially others like subtitles or chapter headings) all packaged together.
  • A container isn't limited to exactly one video stream and one audio stream — it can hold several of each.
Practice — Test Yourself

These questions only cover what THIS subsection taught — Huffman coding, RLE, lossy compression, and video/multimedia packaging (completes Chapter 1).

Short answer 1
Why must text files always use LOSSLESS compression?
Reveal answer

Losing even a small amount of information could corrupt or change the actual meaning of the text — unlike sound/images, there's no "acceptable" amount of information to lose.

Short answer 2
What is the "prefix property" in Huffman coding, and why does it matter?
Reveal answer

No code is the starting sequence of any other (longer) code. It matters because it guarantees a decoder can always tell exactly where one variable-length code ends and the next begins, with zero ambiguity.

Fill in the blank 3
Run-length encoding is especially effective for compressing files with large runs of the ______ repeated bit pattern.
Reveal answer

The SAME repeated bit pattern.

Spot the error 4
A student compresses video by applying an image-compression technique (targeting spatial redundancy) to each frame independently, calling this "efficient". Why is this criticised in the theory above?
Reveal answer

It's unlikely to be efficient, because it ignores TEMPORAL redundancy — the fact that one video frame is usually very similar to the one immediately before it. A much more effective approach records mainly the DIFFERENCES between adjacent frames instead.

Applied / scenario 5
Given the Huffman code table above, decode the bit stream 011010.
Reveal answer

Reading left to right, matching the shortest valid code at each step (the prefix property guarantees this is always unambiguous): 01 = t, 10 = e, 10 = e. The decoded text is "tee".

Short answer 6
Why does a video file need a "multimedia container format" rather than just concatenating a video file and an audio file together?
Reveal answer

Because the audio and visual streams must stay SYNCHRONISED while being handled independently (they go to different parts of the playback system) — a container format is specifically designed to hold multiple streams together while preserving that synchronisation, rather than treating them as two entirely separate files.
