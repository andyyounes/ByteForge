7.04 Library Programs
Why "reinventing the wheel" is a genuinely bad idea in programming — and how object code actually gets linked together.
Key Terms
Object code
Machine code produced by a compiler — cannot be executed by itself until linked.
DLL
Dynamic Link Library — routines loaded into memory that can be shared by multiple processes at once.
Theory

"Library program" is a slightly misleading term

  • A library program is defined as a program contained in a program library — but both terms are misleading.
  • More often, what's in a "library" are SUBROUTINES that programmers can use in their own programs, rather than complete standalone programs.

Why using existing library routines is almost always the right choice

  • There's no advantage to a programmer "reinventing the wheel" — if a routine already exists in a library, writing your own version instead would be UNWISE.
  • Existing library routines have been EXTENSIVELY tested before release.
  • Even if residual bugs remained after testing, the routine's REGULAR, widespread use makes eventual detection of those bugs almost inevitable.
  • Example: the NAG (Numerical Algorithms Group) library — over 1,600 procedures for maths/statistics, developed since 1971, and universally accepted as being about as reliable as software ever gets.

From source code to a runnable program — the linking step

  • If a compiler translates source code with no errors, it produces OBJECT CODE (machine code) — but this object code CANNOT be executed by itself.
  • It must be LINKED with the object code of any subroutines it uses. Linking can happen BEFORE the combined code is loaded into memory and run.

Dynamic linking — a genuinely different approach

  • By contrast, DYNAMIC linking has the routines from a Dynamic Link Library (DLL) already sitting IN memory.
  • WHILE the program is running, it links to whichever DLL routine it needs, at the moment it needs it.
  • A DLL exists specifically so its routines can be SHARED — MORE THAN ONE process can dynamically link to the same DLL file at the same time.
Practice — Test Yourself

These questions only cover what THIS subsection taught — library programs and linking (completes Section 7.04).

Short answer 1
Why are both "library program" and "program library" described as slightly misleading terms?
Reveal answer

What's stored is more often SUBROUTINES that programmers incorporate into their own programs, rather than complete standalone programs.

Short answer 2
Give two reasons why using an existing library routine is better than writing your own version.
Reveal answer

Existing routines have been extensively tested before release; and even residual bugs are almost inevitably caught eventually because of the routine's regular, widespread use.

Fill in the blank 3
Object code produced by a compiler cannot be executed by itself — it must first be ______ with the object code of any subroutines it uses.
Reveal answer

Linked.

Spot the error 4
A student says: "Static linking and dynamic linking are the same thing — both combine object code with routine code before the program starts running." What's wrong?
Reveal answer

Static linking happens BEFORE loading and running. Dynamic linking is different — the DLL routines are already sitting in memory, and the program links to the specific routine it needs WHILE it's actually running, not beforehand.

Applied / scenario 5
Two different applications are running at the same time and both need a shared graphics routine. How does a DLL make this efficient, according to this lesson?
Reveal answer

A DLL is specifically designed to be SHARED — more than one process can dynamically link to the same DLL file at the same time, so the routine doesn't need to be duplicated separately for each application.

Short answer 6
Give one real example of a library mentioned in this lesson, and roughly how many routines it contains.
Reveal answer

The NAG (Numerical Algorithms Group) library — over 1,600 procedures for mathematical and statistics processing.
