1.3c Lossless Compression & Run-Length Encoding (RLE)
Compression that never throws data away — and RLE, the technique that exploits long runs of repeated data.
Key Terms
Lossless compression
Compression where ALL original data can be reconstructed exactly — nothing is permanently discarded.
Run-length encoding (RLE)
A lossless compression technique that shrinks runs of identical, adjacent data into a (count, value) pair.
Run
A sequence of identical, adjacent data items — e.g. five identical characters in a row.
Flag
A special marker value that tells the decoder "the next two values are a (count, code) pair", used when a run is too short to compress on its own.
Theory

Lossless compression

  • With lossless compression, ALL data from the original uncompressed file can be reconstructed — nothing is lost.
  • This matters for files where any data loss would be disastrous — e.g. a large, complex spreadsheet, or a downloaded application/program.
  • Run-length encoding (RLE) is one lossless technique, usable across many file formats.

How RLE works

  • RLE reduces the size of a string of adjacent, IDENTICAL data (e.g. repeated colours in an image, or repeated characters in text).
  • A repeating run is encoded as TWO values: the COUNT of identical items in the run, and the CODE of that data item (e.g. its ASCII code for a character).
  • RLE only works well where there's a genuinely LONG run of repeated units — it's not effective on data that constantly changes.
Worked example — RLE on text

String: aaaaabbbbccddddd — 16 characters, 16 bytes uncompressed (1 byte/char, ASCII).

RLE encoding (count, ASCII code):

05 97   04 98   02 99   05 100

This means: 5 characters of ASCII 97 ('a'), 4 of ASCII 98 ('b'), 2 of ASCII 99 ('c'), 5 of ASCII 100 ('d'). That's 8 numbers = 8 bytes — exactly half the original file size.

The problem case, and the "flag" fix

RLE struggles with a string like cdcdcdcdcd — there's no long run to compress, so naive RLE can make the file BIGGER, not smaller.

The fix: a flag value precedes a genuine (count, code) pair. Without a flag, the next byte(s) are taken at face value with an assumed run of 1 (e.g. 01 99 = one character of ASCII 99).

Example string: aaaaaaaa bbbbbbbbbb c d c d c d eeeeeeee (32 characters, 32 bytes uncompressed)

Without a flag: 08 97 10 98 01 99 01 100 01 99 01 100 01 99 01 100 08 101 → 18 values = 18 bytes.

With flag 255 (only added before genuine runs worth compressing): 255 08 97 · 255 10 98 · 99 100 99 100 99 100 · 255 08 101 → 15 values = 15 bytes, a ~53% reduction.

RLE on a black & white image — the letter 'F'

An 8×8 grid, 1 byte per square: white = 1, black = 0.

Compressed RLE: 9W 6B 2W 1B 7W 1B 7W 5B 3W 1B 7W 1B 7W 1B 6W (using W=1, B=0). The uncompressed grid needs 64 bytes; the RLE version has 30 values — needing only 30 bytes.

RLE on a coloured image

Each pixel here needs 3 bytes (one each for red, green, blue). An 8×8 coloured image uncompressed = 8 × 8 × 3 = 192 bytes.

The RLE-compressed version of that same image needs only 92 bytes (92 values, one byte each) — a file size reduction of about 52%.

Pseudocode — basic RLE encoder (single run)DECLARE data : ARRAY OF CHARACTER DECLARE count : INTEGER DECLARE i : INTEGER count ← 1 i ← 1 WHILE i < LENGTH(data) IF data[i] = data[i - 1] THEN count ← count + 1 ELSE OUTPUT count, ASCII(data[i - 1]) count ← 1 ENDIF i ← i + 1 ENDWHILE OUTPUT count, ASCII(data[LENGTH(data) - 1])
Practice — Test Yourself

These questions only cover what THIS subsection taught — lossless compression and RLE.

Short answer 1
What is the key difference between lossy and lossless compression, in terms of what can be reconstructed?
Reveal answer

Lossless compression allows the ORIGINAL file to be reconstructed EXACTLY, with no data lost. Lossy compression permanently discards some data, so the exact original can never be recovered.

Short answer 2
The string "eeeeeeee" (8 identical characters) is RLE-encoded as 08 101. Explain what each of the two numbers represents.
Reveal answer

08 is the COUNT — how many identical characters are in the run (8). 101 is the CODE — the ASCII code of the repeated character ('e').

Fill in the blank 3
RLE only compresses data effectively when there is a long ______ of ______ units.
Reveal answer

Blank 1: run. Blank 2: repeated (identical).

Spot the error 4
A student says: "RLE always makes a file smaller, no matter what the data looks like." Using the "cdcdcdcdcd" example, explain what's wrong with this claim.
Reveal answer

A string like "cdcdcdcdcd" has NO long runs of identical adjacent characters — every character is different from its neighbour. Naive RLE on this actually makes the file BIGGER, not smaller (each character needs its own count+code pair). A flag scheme is needed to avoid wasting space on non-runs.

Applied / scenario 5
A company needs to compress large spreadsheets containing critical financial data, where even a single incorrect digit could cause serious problems. Should they use a lossy or lossless technique? Justify your answer using this lesson's content.
Reveal answer

Lossless — the lesson explicitly states that lossless compression is important for files where data loss would be "disastrous", giving a large/complex spreadsheet as its own example. Losing even a single value from a financial spreadsheet could be genuinely catastrophic, so a lossy technique (which permanently discards data) is not appropriate here.

Short answer 6
For the coloured 8×8 image example, what was the uncompressed file size, and by roughly what percentage did RLE reduce it?
Reveal answer

Uncompressed: 192 bytes (8 × 8 × 3 bytes per pixel for RGB). RLE reduced it to 92 bytes — a reduction of about 52%.
