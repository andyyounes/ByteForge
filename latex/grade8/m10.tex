\begin{frame}{Every real app starts with loading data}
    \large
    \begin{itemize}
        \item Loading \texttt{questions} and \texttt{answers} as two SEPARATE lists, always appended together, keeps them lined up
        \item \texttt{questions[i]} and \texttt{answers[i]} always belong to the same row.
    \end{itemize}
\end{frame}


\begin{frame}{Writing a file, then reading it back to prove it}
    \large
    \begin{itemize}
        \item \texttt{open(..., "w")} writes; a SEPARATE open afterward reads it back
        \item Proving the save genuinely persisted, not just that the write command ran.
    \end{itemize}
\end{frame}


\begin{frame}{A real leaderboard from accumulated data}
    \large
    \begin{itemize}
        \item Reading many appended entries back in and sorting is exactly how a real leaderboard works. \texttt{enumerate()} gives both position and value for a ranked display.
    \end{itemize}
\end{frame}


\begin{frame}{What separates "working" from "finished"}
    \large
    \begin{itemize}
        \item Code that works perfectly but shows the player nothing isn't really finished. \texttt{except FileNotFoundError:} means the app survives even if a data file goes missing.
    \end{itemize}
\end{frame}

\begin{frame}{Real-World Examples}
    \large
    \begin{itemize}
        \item Every shipped quiz app, leaderboard, or scoring system went through exactly this: load real data, score it, save results, then handle the real world not always cooperating (a missing file, unexpected input)
        \item Never just crashing.
    \end{itemize}
\end{frame}


\begin{frame}{Let Them Discover}
    \Large
    Before opening the platform: what's ONE thing that could realistically go wrong with your data app (a missing file, an empty list, bad input)? Real developers plan for at least one of these before calling anything "finished".
\end{frame}
